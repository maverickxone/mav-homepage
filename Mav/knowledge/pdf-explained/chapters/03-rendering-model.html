不是文字，是画：PDF 的渲染模型

3.1 页面描述语言的本质

3.1.1 PDF 页面 = 一张画布 + 一串绘图指令

上一章我们看到了页面内容流里的这行代码：

BT /F1 24 Tf 100 700 Td (Hello PDF!) Tj ET

让我们逐个操作符拆解：

指令 含义
BT Begin Text——开始文字绘制块
/F1 24 Tf 使用字体 F1，大小 24 点
100 700 Td 移动到坐标 (100, 700)
(Hello PDF!) Tj 在当前位置画出 "Hello PDF!"
ET End Text——结束文字绘制块

注意用词：是"画出"，不是"写入"。对 PDF 渲染引擎来说，画一个字母 'H' 和画一条线段在本质上没有区别——都是在画布的某个坐标上放置一个图形。

3.1.2 坐标系

PDF 使用笛卡尔坐标系，原点在页面左下角：

         (0, 842)                    (595, 842)
            ┌─────────────────────────────┐
            │                             │
            │         ↑ y                 │
            │         │                   │
            │         │                   │
            │         └───→ x             │
            │                             │
            │                             │
            └─────────────────────────────┘
         (0, 0)                      (595, 0)

单位是点（point），1 点 = 1/72 英寸 ≈ 0.353mm。A4 纸是 595 × 842 点。

这与屏幕坐标系不同——屏幕通常原点在左上角，y 轴向下。阅读器内部需要做坐标翻转。

3.1.3 图形状态机

PDF 的渲染模型是一个状态机。在任意时刻，都有一组"当前状态"参数在生效：

  • 当前字体和字号
  • 当前颜色（填充色和线条色）
  • 当前变换矩阵（CTM）——控制平移、旋转、缩放
  • 当前裁剪路径
  • 线条宽度、连接方式、虚线模式
  • 透明度

状态可以通过 q（保存）和 Q（恢复）操作符压栈/弹栈：

q                    % 保存当前状态
  1 0 0 1 50 50 cm  % 平移 (50, 50)
  0.5 0 0 rg        % 设置填充色为绿色
  0 0 100 100 re f  % 画一个 100x100 的绿色矩形
Q                    % 恢复之前的状态（位移和颜色都回去了）

3.2 文字渲染：核心陷阱

3.2.1 "画字"而不是"存字"

这是理解 PDF 最关键的认知转变。看这段真实的内容流：

BT
/F1 12 Tf
1 0 0 1 72 720 Tm
<0048> Tj
<0065> Tj
<006C> Tj
<006C> Tj
<006F> Tj
ET

每个 <00XX> Tj 是在画一个 glyph（字形）。0048 不是 Unicode 码点，它是字体内部的 glyph ID。阅读器要通过字体的 CMap（字符映射表）才能知道这个 glyph 对应什么 Unicode 字符。

更常见的写法会把多个 glyph 一次性画出来：

BT
/F1 12 Tf
72 720 Td
[(H) -10 (ello) 20 ( W) -15 (orld)] TJ
ET

这里的 TJ 操作符接受一个数组，数组中：

  • 字符串部分 (H) 表示要画的文字
  • 数字部分 -10 表示水平位移微调（单位是千分之一字号）

这些位移是干嘛的？字距调整（kerning）。比如 "AV" 两个字母紧贴，"LT" 之间要留点空隙。生成器会预先计算好每对字母之间的精确间距，直接写进内容流。

3.2.2 为什么复制粘贴会乱码

当你从 PDF 里 Ctrl+C 复制一段文字时，阅读器需要做逆向映射：

内容流中的 glyph ID → 查 CMap 表 → 得到 Unicode 字符 → 放进剪贴板

问题出在哪里？

  1. 有些 PDF 没有 CMap 表。如果生成器没有嵌入 Unicode 映射，阅读器就无法将 glyph ID 还原为字符。你复制出来的就是乱码或空白。

  2. 自定义编码。有些字体（尤其是 Type 3 字体）使用完全自定义的编码方案，比如把 glyph ID 1 映射到一个数学符号，而不是 ASCII 中的 'A'。

  3. 字体子集化后的重编码。为了减小文件体积，生成器通常只嵌入文档中用到的字符（子集化）。子集化后，glyph ID 可能被重新编号。如果没有同时嵌入 /ToUnicode 映射表，逆向映射就断了。

3.2.3 一个具体的灾难场景

假设一份用 LaTeX 生成的数学论文，里面有这个公式：

$\int_0^{\infty} e^{-x^2} dx = \frac{\sqrt{\pi}}{2}$

在 PDF 内部，积分号 ∫ 可能来自 CMR 字体，e 来自另一个数学字体，上标和下标通过坐标偏移实现。内容流大概长这样：

BT
/F3 12 Tf 200 400 Td <02> Tj          % 画积分号
/F1 8 Tf 0 -4 Td <03> Tj              % 下标 0（向下偏移 4 点）
/F1 8 Tf 0 16 Td <04> Tj              % 上标 ∞（向上偏移）
/F2 12 Tf 15 -6 Td <05> Tj            % 画 e
/F2 8 Tf 0 6 Td <06> Tj               % 上标里的内容
...
ET

如果你试图从这份 PDF 里复制这段公式，得到的极大可能是一堆无意义的字符碎片。因为：

  • 每个符号来自不同字体，各有各的编码
  • 上下标是通过坐标偏移实现的，不是语义上的"上标"
  • 没有任何信息表明"这些符号合起来是一个积分表达式"

3.2.4 文字顺序 ≠ 视觉顺序

更隐蔽的问题：PDF 内容流中文字的绘制顺序不一定等于阅读顺序。

考虑一个两栏排版的页面。生成器可能先画左栏的全部内容，再画右栏；也可能逐行交替绘制。甚至有些生成器为了优化字体切换次数，会把同一字体的所有文字集中画完，再换字体画其他文字。

这对人眼没有影响——最终画出来的页面看起来是对的。但如果你试图提取文字（搜索、复制、或者给 AI 读），就需要一个复杂的文字重排算法来猜测正确的阅读顺序。

3.3 图形绘制

3.3.1 路径与形状

PDF 使用类似 PostScript 的路径绘制模型：

% 画一个三角形
200 200 m          % moveto: 移动到 (200, 200)
300 400 l          % lineto: 画线到 (300, 400)
400 200 l          % lineto: 画线到 (400, 200)
h                  % closepath: 闭合路径
S                  % stroke: 描边

操作符表：

操作 说明
m moveto——移动画笔
l lineto——画直线
c curveto——三次贝塞尔曲线
v, y 简化的贝塞尔曲线
h closepath——闭合路径
re rectangle——画矩形
S stroke——描边
f fill——填充
B 既描边又填充
n 不画（用于裁剪路径）

3.3.2 贝塞尔曲线

PDF 中所有的曲线都用**三次贝塞尔曲线（cubic Bézier curve）**表示。四个控制点 P0、P1、P2、P3 定义一条曲线：

$B(t) = (1-t)^3 P_0 + 3(1-t)^2 t \cdot P_1 + 3(1-t) t^2 \cdot P_2 + t^3 P_3, \quad t \in [0, 1]$

圆形、椭圆、曲线文字——所有这些都用贝塞尔曲线近似。一个圆需要 4 段贝塞尔曲线拼接。

字体中的每个字母轮廓也是贝塞尔曲线的集合。当 PDF 渲染引擎"画"一个 'S' 字母时，它实际上是在渲染一组贝塞尔曲线围成的封闭区域。

3.3.3 变换矩阵

PDF 使用 3×3 仿射变换矩阵的简化形式（6 个参数）来实现平移、旋转、缩放和倾斜：

a b 0
c d 0
e f 1

写在内容流中是 a b c d e f cm。常见变换：

% 平移到 (100, 200)
1 0 0 1 100 200 cm

% 缩放 50%
0.5 0 0 0.5 0 0 cm

% 旋转 45°
0.707 0.707 -0.707 0.707 0 0 cm

图片在 PDF 中也是通过变换矩阵来定位的——先把图片映射到 1×1 的单位正方形，再通过 CTM 变换到页面上的目标区域。

3.4 颜色空间

3.4.1 PDF 支持的颜色模型

PDF 支持多种颜色空间，满足从屏幕显示到印刷输出的不同需求：

颜色空间 用途 示例指令
DeviceGray 灰度 0.5 g（50% 灰）
DeviceRGB 屏幕显示 1 0 0 rg（红色填充）
DeviceCMYK 印刷输出 0 1 1 0 k（品红+黄=红）
CalRGB / CalGray 校准色彩 带白点和 gamma 参数
ICCBased ICC 配置文件 精确的设备无关色彩
Indexed 调色板 最多 256 种预定义颜色
Separation 专色 印刷中的 Pantone 色
Pattern 图案填充 平铺或着色图案

为什么需要这么多颜色空间？因为 PDF 要同时满足屏幕浏览和印刷输出。在屏幕上你用 RGB，在印刷厂你用 CMYK，而且同一个 RGB 值在不同显示器上看起来不一样——ICC 配置文件就是为了解决这个色彩一致性问题。

3.4.2 透明度与混合

PDF 1.4 引入了透明度模型——这是一个比想象中复杂得多的特性。

/GS1 gs              % 设置图形状态（包含透明度参数）
0 0 1 rg             % 蓝色
0.5 0 0 0.5 100 100 cm
0 0 200 200 re f     % 画一个半透明蓝色矩形

图形状态中的 /CA（描边透明度）和 /ca（填充透明度）参数控制不透明度（0 = 完全透明，1 = 完全不透明）。

复杂之处在于混合模式（Blend Mode）——PDF 支持和 Photoshop 一样的混合模式（Normal、Multiply、Screen、Overlay 等），以及**隔离组（Isolated Group）和淘汰组（Knockout Group）**的概念。

渲染带透明度的 PDF 页面需要从后往前合成所有图层——这是 PDF 渲染器性能开销最大的操作之一。很多"PDF 打开慢"的情况，是因为页面中有大量半透明元素需要逐层合成。

3.5 一个真实页面的内容流

让我们看一个稍微复杂但真实的例子——一段包含标题、正文、色块的页面内容：

q                                    % 保存状态
  % 背景色块
  0.95 0.95 0.98 rg                  % 浅灰蓝色
  0 792 612 -80 re f                 % 页面顶部 80 点高的色条

  % 标题
  BT
    /F2 28 Tf                        % 粗体字体，28 点
    0.1 0.1 0.15 rg                  % 深色
    72 740 Td                        % 定位
    (Chapter 3: Rendering) Tj        % 画标题
  ET

  % 正文段落
  BT
    /F1 11 Tf                        % 正文字体，11 点
    0.2 0.2 0.25 rg                  % 正文色
    72 680 Td                        % 起始位置
    12 TL                            % 行距 12 点
    (PDF uses a painting model.) Tj T*
    (Each page is a blank canvas.) Tj T*
    (Content is drawn in order.) Tj
  ET

  % 一条分隔线
  0.8 0.8 0.85 RG                    % 线条颜色
  0.5 w                              % 线宽 0.5 点
  72 660 m 540 660 l S               % 画线
Q                                    % 恢复状态

T* 表示"换行"（按 TL 设定的行距向下移动）。注意文字仍然是逐字符定位的——"换行"只是坐标偏移，不存在语义上的"段落"概念。

3.6 核心洞察：为什么 PDF "不适合被机器理解"

从本章的内容中，我们可以总结出 PDF 渲染模型的三个根本特征——也正是这三个特征让 PDF 成为文字提取和 AI 处理的噩梦：

  1. 视觉驱动，非语义驱动：PDF 关心的是"在哪里画什么"，不关心"这段文字的含义是什么"。没有段落、没有标题层级、没有列表——只有坐标和字形。

  2. 绘制顺序 ≠ 阅读顺序：内容流中对象的出现顺序是为了优化渲染效率，不是为了反映人类的阅读路径。

  3. 字符身份模糊：一个 glyph 不一定能唯一映射回一个 Unicode 字符。连字（ligature）、自定义编码、缺失的 ToUnicode 表都会导致映射失败。

PDF 被设计用来给人看，不是用来给机器读的。 这个设计哲学贯穿整个格式的三十年历史，也是为什么到了 2026 年，从 PDF 中准确提取结构化信息仍然是一个未解决的难题。

我们会在第 9 章详细讨论 AI 时代如何应对这个挑战。
