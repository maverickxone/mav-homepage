以太坊与智能合约

信息更新至 2026-07-13

4.1 钩子：比特币脚本不够用时，Vitalik 看到了什么？

4.1.1 一个只能“转账”的网络

2013 年，还在给比特币杂志写稿的 Vitalik Buterin 注意到一件怪事：比特币的脚本精巧又安全，却像一把只能开锁的螺丝刀——它能规定“这笔钱谁能花”，却很难表达“如果众筹目标没达到，就把钱退回去”，或者“谁先在链上提交正确答案，奖金就归谁”。

比特币脚本的设计哲学是刻意限制。它只处理与花费条件相关的简单逻辑：签名验证、时间锁、多签。这样做的好处是整条网络容易验证、攻击面小；代价是，任何稍微复杂的规则都得在链外实现，链上只留下一笔转账记录。

Vitalik 想：如果区块链不仅能记录“谁转给谁多少钱”，还能保存一段程序，并且让全网节点都按同一段程序执行，会怎么样？

这个想法直接催生了以太坊。以太坊解决的核心问题是：怎样让区块链从“转账账本”升级成“公开可验证的通用计算平台”。

4.1.2 世界计算机的草图

以太坊的蓝图可以概括得很短：链上保存程序和数据，用户通过交易触发程序运行，所有节点在同一套规则下算出同样的结果。

这段保存在链上的程序就是智能合约。它解决的是“链上规则自动执行”的问题：一旦部署，合约代码公开可见，任何人都能调用，网络会共同执行，不需要某个人或某家公司持续维护。

**关键直觉**：比特币是“不可篡改的账本”，以太坊是“不可篡改的账本 + 不可篡改的程序运行环境”。ETH 不只是币，也是驱动这台世界计算机的燃料。

2013 年底，Vitalik 发布了以太坊白皮书；2015 年，以太坊主网上线。接下来几节，我们会跟着 Alice 和 Bob 的钱包，把这条“从点击按钮到链上状态更新”的完整链路走一遍。

4.2 账户模型 vs UTXO

4.2.1 UTXO：像数字钞票

在比特币里，Alice 的余额不是数据库里的一行数字，而是一堆“还没花出去的输出”。每个输出就像一张固定面额的数字钞票：谁拥有对应的私钥，谁就能把它花掉。

假设 Alice 收到了两笔比特币，一笔 0.7 BTC，一笔 0.5 BTC。她想给 Bob 转 0.9 BTC 时，必须同时把这两张“钞票”撕掉，再创造出三张新钞票：0.9 BTC 给 Bob、0.299 BTC 找回给自己、0.001 BTC 作为手续费付给矿工。

比特币 UTXO 的一次支付：

输入：Alice 的 0.7 BTC 输出 + Alice 的 0.5 BTC 输出
            │
            ▼
输出：Bob 0.9  +  Alice 找零 0.299  +  手续费 0.001

UTXO（Unspent Transaction Output，未花费交易输出）解决的是“防止同一笔钱被花两次”的问题：每一张钞票只能花一次，花掉后旧输出失效，新输出诞生。账本里不存在一个可以被反复修改的“余额字段”。

4.2.2 账户模型：像银行余额表

以太坊没有采用 UTXO，而是采用账户模型。在这个模型里，每个地址对应一条账户记录，里面直接保存余额、交易序号和其他数据。

当 Alice 给 Bob 转账 0.9 ETH 时，链上的状态变化非常直接：

以太坊账户模型的一次支付：

Alice 的余额：2.0 ETH  ──►  1.1 ETH
Bob 的余额：  1.0 ETH  ──►  1.9 ETH
Alice 的交易序号 nonce：12  ──►  13

账户模型解决的是“用更自然的方式表达账户状态”的问题：余额可以直接增减，合约也能长期保存复杂数据，不需要把状态拆成一张张钞票。

为了让每笔交易都有唯一顺序，以太坊给每个外部账户配了一个nonce（交易序号）。它解决的是“防止交易被重放或乱序”的问题：Alice 的 nonce 为 12 时，下一笔交易必须使用 12，成功上链后变成 13。如果有人把她的旧交易重新广播，节点会因为序号已经用过而拒绝。

**一句话对比**：UTXO 像现金钱包，付款要找零；账户模型像银行账户，余额直接扣。两者都能防止双重支付，只是记账方式不同。

4.3 以太坊交易与 Gas

4.3.1 从点击按钮到状态更新

Alice 参加了一个学习小组，大家约定每完成一次阅读打卡，就在链上共享的计数器里加一。她打开网页钱包，点击“计数加一”。从这一秒到 count 从 7 变成 8，背后会发生一连串事情。

  1. 钱包构造交易。 钱包写入合约地址、要调用的函数、当前 nonce、Gas 上限，并用 Alice 的私钥签名。
  2. 交易进入网络。 钱包把签名后的交易发给一个以太坊节点。节点检查签名、nonce、余额等基本条件，再把它放进交易池（mempool）。
  3. 验证者把交易放进区块。 以太坊把时间切成约 12 秒一段，每一段叫一个 slot。协议为每个 slot 指定一名区块提议者，提议者从交易池里挑选交易、按顺序执行，并组成候选区块。
  4. EVM 执行合约。 提议者的**以太坊虚拟机（EVM）**找到计数器合约，读出旧值 7，执行加一，得到 8。
  5. 其他节点独立复核。 其他节点收到候选区块后，也会按相同顺序执行交易。只要输入和旧状态相同，它们就会得到同样的新状态。
  6. 结果写入新的世界状态。 调用成功时，count 更新为 8，Alice 支付实际消耗的交易费，并拿到一张交易收据。如果调用失败或 Gas 耗尽，本次状态变化会回滚，但已消耗的 Gas 仍然计费。
Alice 的钱包
    │  构造交易并签名
    ▼
交易池（mempool）
    │  区块提议者选择交易
    ▼
候选区块
    │  各节点用 EVM 独立执行
    ▼
成功：count 由 7 变成 8，生成交易收据
失败：状态回滚，已耗 Gas 仍收取

交易池解决的是“交易在被打包前暂存在哪里”的问题：它像一个公共候车厅，所有等待上链的交易都在这里排队，供提议者挑选。

区块提议者解决的是“这一轮谁来决定交易顺序”的问题：每个 slot 只有一名提议者负责构造候选区块，其他人负责验证和投票。

EVM 解决的是“所有节点怎样执行出相同结果”的问题：它为智能合约提供统一的运行环境，不同节点用同样的输入跑同一段字节码，必须得到同样的输出。

4.3.2 世界状态与两类账户

以太坊把所有账户及其数据的总和称为世界状态。它像一张覆盖全网的当前快照，每个区块都在上一张快照上依次执行交易，得到下一张快照。

世界状态里有两类账户：

  • **外部账户（EOA）**由私钥控制。普通钱包地址属于这一类。它能主动发起交易，主要保存 ETH 余额和 nonce。
  • 合约账户由代码控制。它保存程序代码和长期数据，没有私钥，不能主动发起交易；只有当外部账户或另一个合约调用它时，它才按代码执行。

“谁能发出命令”和“命令执行什么规则”就这样被分开了：外部账户用私钥表达授权，合约账户用公开代码决定结果。

世界状态解决的是“全网如何维护同一份当前数据”的问题：每个节点都保存一份状态副本，通过独立执行交易来同步更新，不需要依赖某个中心数据库。

4.3.3 为什么读取合约常常“免费”？

Alice 刷新网页查看计数器当前值时，钱包通常不会发送交易，而是请某个节点在本地模拟执行。这种本地调用不写入区块，因此不需要支付 Gas。

但如果另一个合约在链上交易中读取 count，这次读取属于链上执行的一部分，仍然会消耗 Gas。区分这两种场景很重要：本地读取免费，链上读取计费。

4.3.4 区块怎样保存执行结果

每个区块保存一组有顺序的交易，以及世界状态的状态根哈希。根哈希可以理解成整份数据的“总指纹”：任何账户余额或合约数据发生变化，根哈希都会变化。

以太坊用带有 Merkle 特性的树形结构组织状态。节点可以用一个短小的根哈希代表庞大的当前状态，也能用一条证明路径验证某项数据确实属于这份状态。对初学者来说，记住“根哈希是状态的指纹”就够了。

4.4 Gas Limit、Gas Price、Base Fee、Priority Fee

4.4.1 Gas 是给计算标价的单位

以太坊允许合约执行循环、修改存储、调用其他合约。这些操作都会消耗全网节点的计算和存储资源。Gas 就是衡量这份资源消耗的统一单位。

一次简单转账消耗的 Gas 较少；写入合约存储、创建合约或执行复杂逻辑会消耗更多 Gas。Gas 还设置了明确边界：如果循环太久或操作太多，执行会耗尽 Gas 并停止，避免某个程序把网络拖垮。

Gas 解决的是“怎样为链上计算定价并设限”的问题：没有 Gas，恶意或失误的合约可能无限运行，占用所有节点资源。

4.4.2 费用由哪些部分组成

理解交易费需要区分两个量：

  • Gas 用量：这次执行实际做了多少工作。
  • Gas 价格：用户愿意为每单位 Gas 支付多少 ETH。

假设计数器调用实际用了 43,000 Gas，当时每单位 Gas 价格是 20 Gwei，那么费用约为：

43,000 × 20 Gwei = 860,000 Gwei = 0.00086 ETH

Gwei 是 ETH 的较小单位，1 Gwei = 10⁻⁹ ETH。用它报价只是因为用 ETH 写一长串小数太不方便。

钱包还会设置一个 Gas Limit（Gas 上限），例如 60,000。它是安全边界：如果执行超过这个上限就会失败，但只按实际用量收费，没用完的部分不会扣走。

在当前费用机制下，每单位 Gas 的价格主要分成两部分：

  • Base Fee（基础费）：由协议根据区块拥堵程度自动调整，这部分会被销毁（burn），不会给任何人。
  • Priority Fee（优先费）：用户额外付给区块提议者的小费，用来激励提议者优先打包自己的交易。

Base Fee 解决的是“在网络拥堵时自动调节需求”的问题：区块塞满时 Base Fee 上涨，空闲时下降，像动态定价的路由器。

Priority Fee 解决的是“让用户表达紧急程度”的问题：愿意多付小费的人，交易更可能被尽快打包。

4.4.3 失败交易也要付费

合约主动拒绝调用，或者执行中耗尽 Gas，本次交易造成的状态修改会回滚。但节点已经完成的签名检查、指令执行和错误处理仍然占用资源，因此已经消耗的 Gas 会照常计费。

**安全提醒**：Gas Limit 不是交易费上限的精确值。它是“工作量上限”，而实际费用 = Gas 用量 ×（Base Fee + Priority Fee）。网络拥堵时，即使 Gas 用量不变，实际花费也可能大幅上升。

4.5 智能合约：从自动售货机开始

4.5.1 自动售货机类比

“智能合约”这个名字容易让人联想到法律文件。它在以太坊里的实际形态更像一台自动售货机：你投入足够金额并选择商品，机器就按照固定规则出货。

智能合约把类似规则写进公开代码，再由区块链网络共同执行。代码部署后，所有人都能看到它的逻辑；调用时，网络会按代码执行，而不是按某个运营人员的心情执行。

这个类比也有一条重要边界：自动售货机只能处理它能识别的硬币和按钮，智能合约也只能处理链上能够得到的数据。涉及商品质量、现实身份和法律争议时，仍然需要链外制度参与。

4.5.2 DApp 的三层结构

用户日常接触的去中心化应用（DApp）通常由三层组成：

  • 网页层：负责展示界面和组织操作。
  • 钱包层：负责用私钥签名交易。
  • 合约层：负责链上的规则与状态。

理解这三层后，许多 DApp 的边界会更清楚。网页只是一个前端，真正改变资产状态的步骤发生在钱包签名和合约执行之后。

4.5.3 合约怎样获得现实数据

EVM 只能稳定处理所有节点都能复现的数据。天气、汇率、比赛结果来自链外，合约无法自行访问网页或 API，否则不同节点可能得到不同结果，破坏共识。

预言机（Oracle） 解决的是“怎样把链外可信数据送上链”的问题：多个数据提供者提交报价，预言机网络聚合后更新链上价格，合约再依据这个价格判断抵押品是否充足或触发结算。

预言机让合约接触现实世界，也把新的信任条件带进系统。使用依赖预言机的合约时，要问清楚数据从哪里来、多久更新一次、异常报价怎么处理。

4.6 Solidity 示例：一个可运行的计数器

4.6.1 计数器合约源代码

下面的合约就是 Alice 学习小组使用的共享计数器。它保留一个数字，允许任何人加一，同时只允许部署者把数字归零。

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract SharedCounter {
    uint256 public count;
    address public owner;

    event CountChanged(uint256 newCount);

    constructor(uint256 initialCount) {
        count = initialCount;
        owner = msg.sender;
    }

    function addOne() external {
        count += 1;
        emit CountChanged(count);
    }

    function reset() external {
        require(msg.sender == owner, "only owner");
        count = 0;
        emit CountChanged(count);
    }
}

这段代码已经包含理解智能合约所需的主要元素：

  • 状态变量 count 和 owner：会长期保存在链上。它们解决的是“合约需要记住什么”的问题。
  • 构造函数 constructor：部署时执行一次，设置初始状态。它解决的是“合约诞生时如何初始化”的问题。
  • msg.sender：表示当前这次调用的直接发起者。它解决的是“谁来负责这次调用”的问题。
  • require：检查条件，不满足时终止执行并回滚。它解决的是“在条件不符时怎样安全地拒绝”的问题。
  • event：在交易收据中写入日志。它解决的是“前端如何高效发现状态变化”的问题。

public 让 Solidity 自动为 count 和 owner 生成读取函数；external 表示函数供合约外部调用。初学时先理解这些词表达的权限和行为即可。

4.6.2 从源代码到一次成功调用

部署者先把源代码编译成 EVM 能理解的字节码，再用钱包发送一笔创建合约的交易。交易成功后，链上产生一个合约地址。构造函数在部署过程中运行，把 initialCount 写入 count，也把部署者记为 owner。

Alice 随后调用 addOne。她的钱包把函数名称和参数编码进交易数据，签名后广播。交易进入区块时，EVM 找到对应函数，执行 count += 1，并写出 CountChanged 事件。

网页看到交易收据后，会重新读取 count 并显示新值。这就形成了一条完整链路：

网页组织操作
  → 钱包展示并签名
  → 合约执行规则
  → 收据记录结果
  → 网页刷新状态

4.6.3 回滚与原子性

假设 Alice 调用 reset。函数先检查 msg.sender 是否等于 owner。条件不满足时，require 会让本次调用失败，count 保持原值，CountChanged 事件也不会留下。

智能合约还可以在一笔交易中连续调用其他合约。只要未被程序专门处理的错误沿着调用链返回，这条调用链产生的状态修改会一起回滚。这种性质叫作原子性。

原子性解决的是“金融操作不能只完成一半”的问题：一次兑换可能同时扣除代币 A、增加代币 B 并更新流动性池，中途失败时系统恢复到交易开始前，避免 Alice 付了钱却没拿到货。

回滚会撤销状态结果，但已经完成的计算仍会消耗 Gas。用户支付的是节点实际做过的工作。

4.7 ERC-20 与授权风险

4.7.1 代币也是合约

以太坊上的代币通常是一份合约状态。ERC-20 是一种通用的代币标准，它规定了合约应该提供哪些函数和事件。符合标准的代币合约会保存一张“地址到余额”的映射。

ERC-20 解决的是“不同代币和应用如何互相兼容”的问题：只要代币遵循同一套接口，钱包就知道怎么查询余额，交易所就知道怎么发起转账，其他合约也知道怎么与它交互。

ETH 本身是以太坊协议层的原生资产；ERC-20 代币的余额则由各自合约管理。Alice 转给 Bob 10 个 USDT 时，USDT 合约从 Alice 的记录中减去 10，再给 Bob 的记录加上 10。

4.7.2 授权：把钥匙交给别人

Alice 钱包里有 300 USDT，她想在一个去中心化交易所兑换其他代币。交易所合约不能直接从 Alice 钱包拿钱，必须让 Alice 先授权。

她发送一笔调用 USDT 合约 approve 函数的交易，在代币合约里写下一条授权记录：

资产拥有者 owner：    Alice
被授权者 spender：    交易所合约
可使用额度 allowance：100 USDT

approve 解决的是“怎样让第三方在限定额度内代为转账”的问题：没有它，自动化合约就无法帮用户完成兑换、借贷等组合操作。

授权成功后，100 USDT 仍然显示在 Alice 的余额中。链上新增的是一项权限：交易所合约以后可以在额度范围内调用 transferFrom，从 Alice 地址转出 USDT。

当 Alice 确认兑换时，交易所合约调用 transferFrom，把约定数量从 Alice 转入资金池，再按规则把另一种资产给 Alice。代币合约同时减少剩余授权额度。

4.7.3 无限授权与恶意网页

有些网页会请求“无限额度”，这样用户以后兑换时可以少做一次授权交易。方便的代价是权限长期存在。合约出现漏洞、升级权限被滥用，或者用户把授权给了钓鱼网站控制的地址时，被授权者可能在很久以后使用剩余额度。

网页关闭、钱包断开连接或浏览器重启，都不会自动删除这条链上权限。Alice 可以再次调用代币合约，把额度改小或设为零；这次修改同样需要签名、上链和 Gas。

**重大风险**：approve 授权是把“未来转走你代币的权力”长期写进合约。钓鱼网站最常见的获利方式不是骗你直接转账，而是骗你给一个恶意地址无限 approve，之后在你睡觉时把资产转走。授权前务必核对网页域名、spender 地址、代币种类和额度。

连接钱包、签署消息、授权代币和直接转账是四件不同的事：

  • 连接钱包：网页只获得公开地址等可见信息。
  • 签署普通消息：地址对某段内容表示同意，具体后果取决于消息用途。
  • approve 授权：指定 spender 获得未来转移某种代币的额度。
  • transfer 转账：代币余额立即按本次交易发生变化。

钱包确认页应当显示被授权合约和额度。只看“确认”按钮，无法判断授予了多大的长期权力。

4.8 真实漏洞：权限、多签、可升级合约与 The DAO

4.8.1 权限来自代码

外部账户的权限来自私钥：谁能产生有效签名，谁就能以这个地址发起交易。智能合约的权限来自代码中的检查条件。

计数器部署时把 owner 设为 msg.sender。reset 函数再次检查当前调用者是否等于 owner。Alice 可以调用 addOne；只有 owner 能成功调用 reset。

真实项目往往会使用多个角色：管理员可以暂停紧急功能，铸币者可以发行代币，普通用户只能转账。权限越大，持有权限的地址就越值得关注。

多签钱包解决的是“单个私钥丢失或泄露怎么办”的问题：m-of-n 多签表示一共有 n 把授权钥匙，每次操作至少需要 m 个有效签名。常见的 2-of-3 钱包有三名签名者，任意两人同意即可执行，降低了单点风险。

可升级合约解决的是“部署后发现 bug 怎么办”的问题：项目方使用代理结构，用户一直调用同一个代理地址，代理再把请求转给当前版本的逻辑合约。升级时，管理员把代理指向新的逻辑版本，原有地址和状态继续使用。

但可升级也赋予管理员改变规则的权力。判断一份合约的真实信任边界时，代码和升级权限需要一起看：管理员是谁、升级需要几人同意、是否有时间锁、用户能否在升级前退出，都直接影响安全。

4.8.2 The DAO 与重入攻击

2016 年，The DAO 是以太坊上一个去中心化风险投资基金，聚集了大量 ETH。一名攻击者利用合约漏洞，把基金里的 ETH 大量转走。这次事件最终导致了以太坊的第一次硬分叉，也催生了后来的 ETC 与 ETH 两条链。

漏洞的核心是重入攻击。假设一个金库合约按下面的顺序处理提款：

检查用户余额
  → 把 ETH 发给用户
  → 最后扣减用户余额

接收 ETH 的地址也可能是一份合约。它收到 ETH 时，可以立刻再次调用金库的提款函数。此时旧余额尚未扣减，第二次检查仍可能通过。攻击者便能在一次调用尚未结束时重新进入同一个函数，反复取钱。

更稳妥的顺序是检查—更新—交互：

检查条件
  → 先扣减余额
  → 最后发送 ETH

重入攻击解决的是“外部调用顺序可能绕过余额检查”的问题——更准确地说，重入风险提醒设计者：在把钱或控制权交给外部地址之前，务必先把自家账本更新好。

成熟合约还会使用重入锁，并接受多轮测试和安全审计。The DAO 事件让这种风险广为人知，也推动了防护方式的普及。

**安全提醒**：阅读任何合约时，先问自己几个问题：谁能调用关键函数？谁能暂停或升级？资金先转移还是状态先更新？价格从哪里来？失败时哪些状态会回滚？这些问题比背诵漏洞名称更能帮你守住资产。

4.9 本章小结

以太坊从比特币的“转账脚本”再往前走了一步：它在链上保存程序和数据，让全网节点共同执行同一段代码。Alice 的一笔调用由钱包构造并签名，进入交易池后由区块提议者按顺序打包，各节点在 EVM 中独立执行，成功结果进入新的世界状态，失败调用则回滚本次状态变化。

账户模型让余额和 nonce 直接挂在地址下，与 UTXO 的“数字钞票”思路形成对照。Gas 衡量链上计算与存储的成本，Gas Limit 是安全边界，Base Fee 动态调节拥堵，Priority Fee 激励优先打包。智能合约把规则写进公开代码，Solidity 的状态变量、构造函数、msg.sender、require 和事件共同支撑起可验证的自动执行。

ERC-20 授权把 spender 和额度长期写入代币合约，网页关闭后权限依然存在，这是最常见的被盗路径之一。The DAO 事件则展示了重入攻击的破坏力：先更新状态、再与外部交互，是合约设计的重要纪律。

读完本章，可以先确认自己能回答三个问题：一笔合约调用由谁发起、由谁提出进入区块、由谁检查执行结果；Gas 上限和实际费用有什么区别；外部账户与合约账户各自受什么控制。下一章，我们会进入共识机制，看看这些区块最终是如何被全网共同承认的。
