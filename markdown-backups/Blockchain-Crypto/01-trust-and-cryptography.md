## 1.1 钩子：为什么 Alice 不能直接给 Bob 转 100 元？

Alice 和 Bob 是同校学生。Alice 欠 Bob 100 元饭钱，她想直接通过手机转过去，不经过微信、不经过支付宝、也不经过银行 App。

"直接转"是什么意思？

她理想的情况很简单：在自己的手机上把 Alice 的余额减 100，在 Bob 的手机上把余额加 100。两个人都确认一下，交易完成。

但稍微一想就会发现不对劲：如果 Alice 的手机显示"已转出"，Bob 的手机却显示"没收到"，该听谁的？如果 Alice 手里其实只有 80 元，她能不能仍然在自己的手机上写下"余额减 100"？如果 Alice 同时给 Bob 和 Carol 各转 100 元，用的是同一份钱，系统能不能发现？

这些问题不是技术细节，而是数字货币最基础的问题：**在没有银行参与的情况下，怎么让一群互不信任的人共同承认一份余额记录？**

银行之所以看起来让这件事变简单，是因为它扮演了三个角色：

1. **账本保管者**：银行数据库里记着每个人的余额。
2. **交易执行者**：你发起转账，银行检查、扣款、入账。
3. **纠纷仲裁者**：出了问题，你可以找银行申诉、冻结、撤销。

本章要做的事，就是把银行这三个角色拆开，看看在没有单一机构的情况下，密码学和公开规则能不能重新拼出一份可信的账本。

:::callout-tip
**先把问题记住，不用记住术语。**

读完这一章，你应该能回答：为什么 Alice 不能只在自己手机上改余额？为什么需要很多人一起记账？为什么密码学能解决授权问题，却不能自动解决"钱够不够"和"哪笔先发生"？
:::

## 1.2 银行做了什么：清算、账本、信任

在讨论"去掉银行"之前，先仔细看看银行到底做了什么。很多人以为转账就是"我的钱变少，你的钱变多"，实际上银行内部至少做了以下几件事。

### 1.2.1 账本：谁有多少钱

银行最核心的资产是一份**账本**（ledger）。账本不是一本实体账簿，而是数据库里的一系列记录：Alice 的账户余额、Bob 的账户余额、每一笔收入和支出。

账本的关键特征是：银行保存着唯一被认可的版本。Alice 说自己有 1000 元不算数，银行数据库里的记录才算数。

### 1.2.2 清算：把一笔交易落实到账本

当你用手机银行给 Bob 转 100 元时，银行会做**清算**（clearance/settlement）：

- 检查 Alice 的余额是否大于等于 100 元；
- 把 Alice 的余额减去 100 元；
- 把 Bob 的余额增加 100 元；
- 记录这笔交易的时间、金额、双方账户。

这个过程中，银行实际上回答了三个问题：这笔钱存在吗？这笔钱属于 Alice 吗？这笔钱之前有没有被花掉？

### 1.2.3 信任：我们为什么相信银行

你之所以敢把钱放在银行，并不是因为银行用了什么神奇的密码学，而是因为你相信一整套制度：法律、存款保险、监管、客服和司法救济。如果银行搞错了，你可以投诉、起诉、要求恢复。

:::callout-tip
**数字货币不是要消灭所有信任。**

比特币的目标不是让世界不再需要银行，而是在某些场景下，把"必须信任某一家机构"变成"可以依据公开规则自行核查"。
:::

### 1.2.4 中心机构也有边界

中心机构能做很多事，但也有一些代价：

- 它可以冻结账户、限制交易、审查资金流向；
- 它需要维护昂贵的数据库和客服体系；
- 它只能服务能开户、能被识别身份的人；
- 跨境转账尤其慢，因为不同国家的银行要互相清算。

这些代价不是"银行坏"，而是说明：银行适合很多场景，但不一定适合所有场景。区块链研究的是另一类场景——参与者分散在全球，彼此没有稳定信任关系，却仍然希望共同维护一份记录。

## 1.3 没有银行时的问题：谁记账、双花、女巫攻击

现在把银行拿掉。Alice 和 Bob 只通过互联网联系，周围还有许多互不相识的节点。新的问题马上出现。

### 1.3.1 谁保存账本

没有银行，账本就不能只存在一个地方。如果 Alice 的手机保存"真实账本"，她随时可以改成对自己有利的版本；如果 Bob 的手机保存，他也一样可以。

所以一个自然的想法是：让很多人各自保存一份账本副本。每次交易发生后，把消息广播出去，让每个副本都更新。但这样又带来新的问题：大家看到的更新顺序可能不同，有人可能故意广播假消息。

### 1.3.2 双花：同一笔钱能不能花两次

这是数字货币最著名的问题，叫作**双花**（double spending）。

现金不会双花：一张 100 元纸币交给 Bob 后，Alice 手里就没有这张纸币了。但数字文件可以无限复制。Alice 完全可以把同一份"价值 100 元"的数字记录复制十次，分别发给十个人。

如果两份交易都带有 Alice 的有效授权，系统该接受哪一份？签名只能证明"Alice 同意这笔交易"，不能单独决定"哪一笔先发生"。

因此，数字货币不能只是"一份写着余额的文件"。它需要一条规则：某份资金一旦在一笔有效交易中被使用，后续交易就不能再次使用它。

### 1.3.3 女巫攻击：一个坏人可以扮演很多人

在一个封闭公司里，可以事先登记服务器身份，规定谁有投票权。但公开网络允许任何人加入，一个人也能创建成千上万个网络身份。

如果简单采用"一台电脑一票"，攻击者只需批量注册账号，就能伪装成多数。这种行为叫作**女巫攻击**（Sybil attack）。

它说明了一个基本事实：**网络身份很便宜，不能直接用来衡量意见的分量。** 你需要某种机制，让"发表意见"和"付出代价"挂钩。

:::callout-tip
**三个核心困难的记忆法：**

- **谁记账**：去掉银行后，没有单一可信账本。
- **双花**：数字文件可复制，需要防止同一笔钱花两次。
- **女巫攻击**：网络身份廉价，不能让一人冒充多人。

比特币的答案会分别对应：公开账本 + 区块排序、UTXO + 区块链、工作量证明。
:::

## 1.4 比特币的全景答案

比特币给出的方案可以先压缩成一段话，先建立一个整体印象，后面再拆开看每一块。

> Alice 用自己的**私钥**对交易做**数字签名**，把交易发给比特币网络。网络中的**全节点**分别检查交易是否合法。**矿工**从有效交易中组织**候选区块**，并通过**工作量证明**竞争记账机会。某个候选区块胜出后，全节点再次独立检查它；符合规则的区块被接到当前**账本**后面，其他矿工继续在新区块之后工作。

这段话已经包含了整套系统。接下来几章会逐一回答其中的问题：签名为什么可信、节点检查什么、矿工怎样竞争、区块怎样连接、以及不同版本出现时网络怎样继续。

现在只需要记住这幅全景图：

```text
Alice 的钱包
    ↓ 生成私钥 / 公钥 / 地址
Alice 组织交易并用私钥签名
    ↓ 广播到 P2P 网络
全节点检查签名、资金来源、金额关系
    ↓ 有效交易进入内存池
矿工挑选交易、组织候选区块、做工作量证明
    ↓ 某个区块被网络接受
新区块接入账本，所有节点更新状态
    ↓ 下一轮继续
```

:::callout-tip
**记住流程，不用记住每个词。**

你现在只需要知道：用户负责授权，节点负责检查，矿工负责排序和竞争，公开规则负责统一标准。这四件事分别对应四类参与者，下一节就会讲。
:::

## 1.5 四类参与者

比特币网络中有四类角色。同一台电脑可以同时承担多个角色，但职责要分开理解。

### 1.5.1 用户与钱包

用户通过**钱包**（wallet）软件参与网络。钱包的主要工作是：

- 生成并保管**私钥**、**公钥**和**地址**；
- 组织交易：选择要花掉的旧资金、填写收款地址和金额；
- 用私钥对交易做**数字签名**；
- 把签名后的交易广播到网络。

普通用户不需要挖矿。钱包只负责"发出一笔有效的请求"。

### 1.5.2 全节点

**全节点**（full node）保存着完整的账本副本，并独立执行规则。它的主要工作是：

- 接收交易和区块；
- 检查每笔交易是否合法：签名是否匹配、资金来源是否存在、金额是否平衡；
- 检查每个区块是否符合规则：工作量证明是否合格、矿工奖励是否超额、交易集合是否正确；
- 只把合法内容加入自己的账本副本，并把消息继续转发给邻居。

全节点是比特币"去信任"的核心。你不需要相信某个服务器，可以自己运行一个全节点来验证一切。

### 1.5.3 矿工

**矿工**（miner）的工作是组织候选区块并竞争出块机会。他们会：

- 从全节点那里收集待处理交易（内存池）；
- 把交易组织成一个候选区块；
- 通过大量哈希计算寻找满足难度要求的区块头；
- 找到后把区块广播出去，希望全节点接受。

矿工不能随意改变规则。即使他找到了一个合格的工作量证明，全节点仍会检查区块内容；如果内容不合法，区块会被拒绝。

### 1.5.4 矿池

现实中，单个矿工的算力可能很小，中奖概率很低。**矿池**（mining pool）把大量矿机的算力集中起来，统一分配任务、共享收益。矿池提高了中小矿工收入的稳定性，但也引入了新的信任问题：矿池管理者可能选择哪些交易被打包。

```text
┌─────────────┐    ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│ 用户与钱包   │ → │ 全节点       │ → │ 矿工         │ → │ 矿池（可选） │
│ 创建并签名   │    │ 检查并转发   │    │ 打包并竞争   │    │ 协调算力     │
└─────────────┘    └─────────────┘    └─────────────┘    └─────────────┘
```

:::callout-tip
**一个常见误解：**

"矿工决定比特币规则。"不对。矿工决定的是**哪个候选区块被提交**，但全节点决定**这个区块是否合法**。规则写在软件里，由运行全节点的人共同执行。
:::

## 1.6 哈希函数：数字指纹

现在进入密码学部分。密码学很深，但我们只学理解交易所需的三件工具：**哈希函数**、**公私钥**和**数字签名**。

### 1.6.1 什么是哈希函数

**哈希函数**（hash function）接收任意长度的数据，输出固定长度的结果。你可以把它想象成一台"数字指纹机"：把任何文件放进去，都会得到一个长度固定的指纹字符串；文件只要改一个字，指纹通常会完全不同。

比特币大量使用 **SHA-256** 哈希算法。下面是一个可以实际运行的 Python 例子：

```python
import hashlib

message = "hello".encode("utf-8")
print(hashlib.sha256(message).hexdigest())

# 输出：2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
```

试着把 `"hello"` 改成 `"Hello"`（大写 H），再运行一次。你会发现输出完全变了：

```python
import hashlib

message = "Hello".encode("utf-8")
print(hashlib.sha256(message).hexdigest())

# 输出：185f8db32271fe25f561a6fc938b2e264306ec304eda518007d1764826381969
```

### 1.6.2 哈希的几个重要性质

1. **确定性**：同样的输入一定得到同样的输出。
2. **敏感性**：输入微小的变化会导致输出大范围变化。
3. **单向性**：从哈希值倒推原文，在计算上极其困难。
4. **抗碰撞性**：很难找到两个不同的输入产生相同的输出。

:::callout-tip
**哈希和加密的区别：**

加密需要密钥，接收者可以解密还原原文；哈希只生成一个固定长度的摘要，用来比较"是不是同一份数据"。加密是"可逆的隐藏"，哈希是"不可逆的指纹"。
:::

### 1.6.3 比特币用哈希做什么

在比特币里，哈希承担几项容易理解的工作：

- **交易标识**：每笔交易计算哈希，得到唯一的交易 ID；
- **区块标识**：区块头计算哈希，得到区块 ID；
- **Merkle 根**：一批交易的哈希汇总成一个根哈希；
- **工作量证明**：矿工反复改变区块头并计算哈希，寻找满足难度要求的结果；
- **链式连接**：每个区块头包含前一个区块的哈希，修改旧记录会让后续连接失效。

这些我们会在后面逐一展开。现在只需要一个直觉：**哈希让"数据是否被改动"变成一件可以快速核查的事**。

## 1.7 私钥、公钥、地址

哈希解决的是"数据完整性"问题，但还没有解决"谁有权花这笔钱"。这需要公私钥密码学。

### 1.7.1 私钥：一把不能告诉任何人的钥匙

Alice 的钱包第一次使用时，会生成一个足够随机的巨大整数，这就是**私钥**（private key）。

私钥有多大？比特币使用的私钥是一个 256 位的随机数，可能的取值数量大约是 2 的 256 次方。这个数字大到什么程度？它比宇宙中所有原子的数量还要多得多。

**掌握私钥的人可以授权花费相应资金**。因此私钥需要一直保密，最好离线保存、备份在多个安全位置。

:::callout-warn
**安全警告：私钥丢失无法找回。**

如果你忘记了银行密码，可以拿身份证去柜台重置。但比特币没有客服中心：私钥丢了，对应地址里的钱就永远动不了；私钥被窃，钱可能立即被别人转走。不要把私钥截图保存在手机里，不要把它发给任何人，包括自称"客服"的人。
:::

### 1.7.2 公钥：可以公开的身份标识

钱包通过椭圆曲线运算，从私钥推导出**公钥**（public key）。这个方向计算很快，但从公钥反推私钥，在现实算力下不可行。

你可以把关系记成一条单向推导链：

```text
足够随机的私钥
        ↓ 单向推导
      公钥
        ↓ 与花费脚本组合
   按地址类型处理并编码
        ↓
   对外使用的地址
```

### 1.7.3 地址：收款用的"门牌号"

**地址**（address）是公钥经过处理后的简短表示，用来告诉别人"把钱付到这里"。它通常不会直接写入姓名或现实身份。

比特币地址有多种格式，本书示例会用 `bc1q...` 这样的缩写表示。省略号只代表中间内容被省略，**不能作为真实转账地址使用**。

:::callout-tip
**保护隐私的习惯：**

现代钱包通常会为不同收款生成不同地址。不要反复用同一个地址收钱，这会让别人很容易把你的多笔交易关联起来。
:::

### 1.7.4 为什么比特币选择椭圆曲线

这一节只提供直觉，不参与后续主线。

比特币使用的椭圆曲线系统建立在有限域上的数学运算。私钥可以看作一个巨大范围内的随机整数，公钥则由私钥与公开基点进行标量乘法得到。正向计算高效，已知公钥反推私钥需要解决椭圆曲线离散对数问题，当前通用算法仍需要无法承受的计算资源。

RSA 也能实现公钥密码学，但它依赖大整数分解问题，需要更长的密钥才能达到相近安全强度。比特币交易需要频繁生成和验证签名，较短的椭圆曲线密钥更适合带宽与存储受限的公开网络。

量子计算的发展会影响许多现有公钥系统，包括椭圆曲线签名。这属于长期密码迁移问题，了解基本交易流程后再研究不迟。

## 1.8 数字签名：授权与完整性

有了私钥和公钥，Alice 就可以对一笔交易做**数字签名**（digital signature）。

### 1.8.1 签名解决什么问题

数字签名同时完成两件事：

1. **授权证明**：证明这笔交易是由私钥持有者发起的；
2. **完整性证明**：证明交易内容在签名后没有被改动。

Alice 用私钥对交易内容生成签名，然后把"交易内容 + 签名 + 必要的公钥信息"一起广播出去。节点用 Alice 的公钥验证签名：

```text
Alice 持有：私钥
Alice 发送：交易内容 + 签名 + 必要的公钥信息

节点执行：Verify(公钥, 交易内容, 签名)
结果为真：这份授权与公钥匹配，受保护内容未被改动
结果为假：拒绝交易
```

### 1.8.2 签名不隐藏交易内容

注意，数字签名没有把交易内容隐藏起来。交易金额、输入和输出仍然可以被网络读取。签名提供的是一份可验证的授权证明，不是保密。

如果你希望交易内容保密，需要额外的加密层，比如闪电网络或其他隐私技术。比特币主链默认是公开的。

### 1.8.3 签名能证明什么、不能证明什么

签名能证明："某个私钥授权了这笔交易，并且交易内容没有被改动。"

签名**不能**证明：

- 屏幕前操作的人一定是现实中的 Alice；
- 这笔交易背后的商品或服务一定真实交付；
- Alice 不是被胁迫或被骗签名的。

私钥一旦被盗，攻击者也能生成有效签名。这就是钱包安全如此重要的原因。

### 1.8.4 ECDSA 与 Schnorr 签名

经典比特币交易长期使用 **ECDSA** 签名，Taproot 交易还会使用 **Schnorr** 签名。初学阶段只需要掌握它们共同完成的任务：私钥产生证明，公钥检查证明。具体算法差异属于进阶内容。

## 1.9 Alice 如何签署一笔交易

现在把前面所有工具串起来，看 Alice 给 Bob 转比特币的完整过程。

### 1.9.1 UTXO：不是余额，而是"数字钞票"

假设 Alice 的钱包里显示有 0.5 BTC。比特币账本并没有保存一行"Alice 余额：0.5 BTC"。钱包找到的是一份尚未被花费的交易输出，简称 **UTXO**（Unspent Transaction Output，未花费交易输出）。

你可以先把 UTXO 理解成一张面额为 0.5 BTC、带有特定开锁条件的数字钞票。这张"钞票"的开锁条件通常是"只有对应私钥持有者才能花"。

### 1.9.2 组织一笔新交易

Alice 想给 Bob 支付 0.3 BTC。钱包会创建一笔新交易：

- **输入**：使用那张 0.5 BTC 的数字钞票；
- **输出 1**：0.3 BTC 交给 Bob；
- **输出 2**：约 0.199 BTC 作为找零交回 Alice 的新地址；
- **差额**：约 0.001 BTC 留作手续费给矿工。

```text
旧输出：0.500 BTC，满足 Alice 的签名条件才能花费

新交易：
  输入  0.500 BTC
  输出  0.300 BTC → Bob
  输出  0.199 BTC → Alice 的找零地址
  差额  0.001 BTC → 作为手续费留给打包该交易的矿工
```

这很像用现金买东西：Alice 拿出一张 50 元钞票买一杯 30 元的咖啡，店员找给她 20 元。在比特币里，输入 0.5 BTC 必须全部花掉：0.3 给 Bob，0.199 作为找零回到 Alice 自己的地址，剩下的 0.001 是给矿工的小费。

### 1.9.3 签名与广播

钱包随后用常见的签名范围对这笔交易生成签名，收款条件和全部输出金额都受到保护。如果有人把 Bob 的 0.3 BTC 改成自己的地址，原签名将无法通过验证。

钱包把交易发送给几个直接连接的全节点。每个节点会检查：

- 签名是否有效；
- 输入引用的旧输出是否存在；
- 旧输出是否已经被花掉（防止双花）；
- 输入总额是否足以覆盖输出总额。

通过检查的交易进入该节点自己的**内存池**（mempool），并继续传给邻居节点。

### 1.9.4 尚未确认的状态

这时交易仍然处于"有效但尚未确认"的状态。许多节点已经看见它，矿工也可以选择把它放进候选区块。交易怎样进入区块、怎样得到第一次确认，将在后续章节完整讲解。

:::callout-tip
**UTXO 的直觉：**

不要试图把比特币想象成"账户余额"。把它想象成你钱包里的一叠叠不同面额的数字钞票：每笔交易消耗旧的钞票，生成新的钞票。找零就是新钞票，必须回到你自己的地址。
:::

## 1.10 Merkle 树：把交易压成指纹

一个区块可能包含大量交易。全节点需要一个简洁方法，证明区块中的交易集合没有被悄悄修改。这就是 **Merkle 树**（Merkle tree）的工作。

### 1.10.1 Merkle 树的构造

假设一个区块里有四笔交易 A、B、C、D。先分别计算每笔交易的哈希，再两两组合计算上一层哈希，最后得到一个根哈希：

```text
              Merkle Root
              /         \
          Hash(AB)     Hash(CD)
          /    \       /    \
       Hash(A) Hash(B) Hash(C) Hash(D)
```

任何一笔交易发生变化，比如 C 的金额被改动，Hash(C) 会变，Hash(CD) 会变，最终 Merkle Root 也会变。区块头只需保存这个根哈希，就能为整批交易提供统一指纹。

### 1.10.2 简洁的成员证明

Merkle 树还有一个好处：可以提供简短的成员证明。想证明交易 C 位于区块中，不必传输全部交易，只需给出从 C 通向根节点所需的少量相邻哈希。轻量钱包会利用这类证明减少数据需求。

:::callout-tip
**Merkle 树的本质：**

它把"很多交易是否被改动"这个问题，压缩成"一个根哈希是否匹配"。这让区块头很小，同时仍能保护整个交易集合。
:::

## 1.11 密码学的边界

数字签名可以检查授权与完整性，哈希可以检查数据变化，成熟密码算法可以让伪造在计算上极其困难。但这些保证都有明确边界。

### 1.11.1 密码学不能保证什么

- **不能阻止你主动把私钥交给诈骗者**；
- **不能自动修复钱包软件漏洞**；
- **不能判断链外商品是否真实交付**；
- **不能判断稳定币发行者是否真的持有足额储备**；
- **不能替代现实中的法律责任**。

### 1.11.2 区块链适合什么、不适合什么

区块链适合处理"多方需要共享记录，同时难以共同指定一个中心维护者"的场景。即使满足这个条件，它也会带来速度、成本、隐私和治理方面的代价。

它能证明某个私钥授权了一笔交易，也能为某段数据在大致时间范围内已经存在提供证据。但它无法自动判断链外信息是真是假——比如链上合约看到"货物已经送达"时，仍然需要某个人、设备或服务把现实信息带进系统。

它还能保证符合规则的记录很难被事后改写，却无法保证规则本身合理。一个有漏洞的智能合约可以被准确执行；一个设计失衡的金融协议也可能按照原定规则准确崩溃。

:::callout-tip
**工程上最重要的习惯：**

把问题问完整：哪一步由数学保护，哪一步依赖软件，哪一步依赖运营者，哪一步需要现实世界的数据和制度。不要看到"区块链"三个字就默认一切可信。
:::

## 1.12 本章小结

这一章从"Alice 为什么不能直接给 Bob 转 100 元"这个问题出发，逐步拆开了数字货币的三层困难：谁记账、防止双花、抵抗女巫攻击。

我们建立了比特币网络的全景图：

- **用户与钱包**生成密钥、组织交易、签名并广播；
- **全节点**保存完整账本，独立检查交易与区块是否符合规则；
- **矿工**组织候选区块，通过工作量证明竞争出块机会；
- **矿池**在现实中协调大量矿机，把任务和收益集中管理。

我们也学习了三种密码学工具：

- **哈希函数**为数据生成指纹，让改动可以被快速发现；
- **私钥 / 公钥 / 地址**建立单向推导关系，私钥授权、公钥验证、地址收款；
- **数字签名**绑定授权与交易内容，保证"私钥持有者同意且内容未被改动"。

最后，我们用 Alice 给 Bob 转账的例子，走了一遍交易的实际流程：从 UTXO 的选择、到新交易的组织、到签名广播、再到进入节点的内存池。

:::callout-tip
**读完本章，你应该能回答：**

1. 为什么一种数字货币会被接受？（账本可靠 + 有人愿意接受）
2. 普通用户为什么不需要挖矿？（钱包只负责签名和广播）
3. 签名为什么不能单独解决双花？（签名只证明授权，不能决定交易顺序）
4. 矿工找到结果后为什么还要经过全节点检查？（规则由全节点执行，矿工只能提案）
5. 哈希和加密有什么区别？（哈希是单向指纹，加密是可逆隐藏）
6. Alice 的 0.5 BTC 为什么会变成给 Bob 的输出、找零和手续费？（UTXO 模型：输入必须全部花掉，差额给矿工）
:::
