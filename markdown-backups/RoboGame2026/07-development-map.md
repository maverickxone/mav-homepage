## 从已经走通的路继续向前

故事开始时，上位机只发来一条 `START_MOTION`。现在我们已经知道，这条命令会进入 USART1，经过协议解析和命令分发，再由 `motion_start_motion()` 把 PWM 3000 写到四个电机通道。它证明了新架构的主干已经形成，也给后续开发留下了一条自然路线。

接下来的工作适合像搭桥一样进行。先确认脚下这一段能够稳定承重，再向前接下一段。每接通一个功能，就留下编译、通信和实机证据。这样遇到问题时，可以很快判断故障发生在协议、任务、运动计算、接线还是机械结构上。

```mermaid
flowchart LR
    A["可重复构建"] --> B["协议冒烟测试"]
    B --> C["单轮与轮位验证"]
    C --> D["停止与安全联锁"]
    D --> E["编码器闭环与档位"]
    E --> F["航向与精确运动"]
    F --> G["升降 / 夹爪 / 推杆"]
    G --> H["整车联调记录"]
```

## 先认识工程的几个入口

第一次打开大型嵌入式仓库，很容易在几百个文件之间迷路。这个项目可以沿着命令的实际路径阅读。Keil 工程告诉编译器哪些文件参与构建，`main.c` 告诉芯片从哪里开始运行，`app_task` 则守在新业务的入口。

| 入口 | 阅读时关注的内容 |
| --- | --- |
| `USER/WHEELTEC.uvprojx` | 芯片、编译器、目标名、源码分组和输出设置 |
| `USER/main.c` | `systemInit()`、FreeRTOS 启动和 `app_task` 的创建 |
| `USER/system.c` | USART1、PWM、ICM20948、使能开关和四路编码器初始化 |
| `LOWER_CONTROLLER/APP/app_main.c` | 字节怎样进入协议解析器 |
| `LOWER_CONTROLLER/APP/command_dispatcher.c` | 17 条命令目前各自走向哪里 |
| `LOWER_CONTROLLER/BOARD/` | USART1、115200、PWM 3000 和 A/D/B/C 轮位映射 |
| `LOWER_CONTROLLER/MOTION/motion_controller.c` | 平移、旋转、停止和电机方向引脚 |

遇到“为什么车轮这样转”的问题，可以从 `command_dispatcher.c` 跟到 `motion_controller.c`，再看 `board_motion_config.h` 和 `HARDWARE/motor.h`。遇到“为什么收不到命令”的问题，可以从 `board_uart_config.h` 跟到 `uart_irq.c`、`transport_uart.c` 和协议解析器。沿数据流寻找答案，阅读范围会很快缩小。

## 建立一次可以复现的构建

`USER/WHEELTEC.uvprojx` 是现有 Keil µVision 工程。目标名为 `Mec_Car`，芯片配置为 STM32F407VE，工程记录的编译器是 ARMCC 5.06 update 7，设备包是 `Keil.STM32F4xx_DFP.3.1.1`。这些版本信息很重要，同一份旧工程在另一套编译器上可能出现语法、库或链接差异。

工程把输出目录设为 `OBJ/`，输出名为 `Mec_Car`，并开启 HEX 生成。构建完成后，`fromelf` 会从 `OBJ/Mec_Car.axf` 生成仓库根目录下的 `Mec_Car.bin`，`copyhex.bat` 会把生成的 HEX 复制到根目录。构建前执行的 `hexbinHandle.bat` 会清理旧的 HEX 和 BIN，避免把上一次产物误当成当前结果。

工程文件和批处理脚本记录了 ARMCC 5.06 update 7、AXF、HEX、BIN 的生成过程。仓库还保存了 Windows 程序 `FlyMcu2188.exe`。`源码工程使用指南.pdf` 讲到 target 选择、全量编译和 HEX 产物；FlyMcu 的端口、波特率、芯片选项和 BOOT 状态将在现场烧录时确认并写入记录。

第一次构建的目标很朴素：让 HEAD `fc3ef5d` 在指定工具链中完整编译，并保存错误数、警告数、AXF/HEX/BIN 生成时间和提交号。产物被 `.gitignore` 忽略很正常，构建记录仍可以单独保存。这样，后续源码变化造成编译问题时，会有一个明确的可用基线。

## 在车轮接触地面前验证通信

通信测试可以先让机器人保持静止。USART1 的当前配置是 115200 波特率，协议帧头为 `0xAA 0x55`，payload version 是 `20260612`。`PING` 适合确认收发通道，`GET_PAYLOAD_VERSION` 适合确认上下位机协议版本，`TEST_COMMAND` 可以确认一个 32 位整数能否完整往返。

`TESTS/` 目前只有 README。后续加入的第一个上位机脚本可以依次发送这三条命令，核对 ACK 的原命令序号、命令 ID 和状态，再核对版本或测试 telemetry。随后加入错误 CRC、错误参数长度和未知命令，观察解析器丢弃坏帧、分发器回复 `INVALID_ARGS` 或 `INVALID_COMMAND`。

这一步像先打电话确认双方语言一致。只要 PING、版本和测试值都能稳定往返，接下来的电机问题就可以集中到运动层与硬件层。

## 让四个通道依次说话

正式测试整车方向前，车轮适合先悬空。`motion_test_motor_channels_loop()` 已经提供一个通道测试：A、B、C、D 分别以 PWM 1200 运行一秒，然后全部停止两秒。当前主任务没有调用它，调试时需要用临时测试入口接入，验证结束后恢复 `app_task`。

观察记录应同时写下“哪个接口获得输出”和“车身哪个轮位转动”。当前配置期望左前接 A、左后接 D、右前接 B、右后接 C。轮位正确后再核对转向，左后和右前使用 `-1` 方向系数。接线变化写入 `board_motion_config.h`，运动层继续使用左前、左后、右前、右后的逻辑顺序。

四个通道逐一确认后，可以发送 `START_MOTION` 的前进、后退、左移、右移，再发送两种 `START_ROTATION`。每次动作后都发送 `STOP_MOTION`，确认 PWM 和方向引脚清零。当前三种 `gear` 都会得到固定 PWM 3000，因此这轮测试关注方向组合和停止效果。

## 先把停止能力接牢

车轮落地前，安全链需要从“收到停止命令就停”扩展到“通信异常和任务异常也能停”。使能开关 PE4 已经初始化，下一步是让 APP 读取它并维护统一的运动许可。所有底盘和执行机构入口都读取这份许可，许可撤销时进入同一个安全停止函数。

命令超时需要周期性检查最后一条有效运动命令的时间。当前 `app_task` 使用：

```c
transport_uart_receive_byte(&byte, portMAX_DELAY);
```

`portMAX_DELAY` 会一直等待下一个字节。要加入超时检查，可以让接收等待按固定周期返回，也可以建立独立的安全任务或软件定时器。无论采用哪种方式，通信安静时也要有代码醒来检查时间。超时长度由上位机发送周期和实车制动测试决定，并写入板级配置和通信约定。

看门狗随后负责发现任务卡死。正常任务定期喂狗，关键任务停止运行时由硬件复位。启动后的默认电机状态、复位原因记录和复位后的输出清零也应一起验证。完成这一步后，串口拔掉、上位机退出、使能关闭和任务停顿都能得到可观察的安全结果。

## 用编码器把档位变成真实速度

当前 PWM 3000 让车轮获得固定驱动，`gear` 还没有参与计算。编码器接入后，可以为微速、慢速和快速档位定义目标轮速，再周期性读取 A、B、C、D 的增量。控制器比较目标与测量值，逐步调整 PWM，这就是速度闭环。

这里需要先测清编码器每圈脉冲数、减速比、轮径、读取周期和正负方向。数据单位统一后，`SENSORS` 对外提供轮速，`MOTION` 管理目标和控制器。原厂 `BALANCE/` 中保留了 PI 控制思路，可以作为参考；新的初始化已经停用原厂 PI 参数，比赛底盘需要结合当前机械结构重新测量和整定。

有了稳定轮速，按时间移动可以使用 FreeRTOS 时钟结束动作，按距离移动可以累计编码器里程。持续动作与精确动作适合由运动状态机管理。**状态机**，英文是 **state machine**，可以想成一张写着“空闲、运行、减速、完成、故障”的流程牌。命令分发器只负责接单和启动状态，运动任务持续执行，新的 `STOP_MOTION` 仍能随时被接收。

## 再补航向和操作机构

按角度旋转和 `GET_HEADING` 需要 ICM20948 提供稳定朝向。开发时先记录静止零漂，再验证缓慢旋转一周时角度是否连续，随后把 heading 接入 `SENSORS` 和 telemetry。编码器负责看轮子走了多少，IMU 负责看车身朝向怎样，两种反馈合在一起可以提高直线和旋转控制的可靠性。

升降、夹爪和推杆适合在底盘安全链稳定后接入。每个机构先完成单独的手动低速动作，再加入限位读取、动作超时和停止，最后连接六条已有协议命令。目标高度、方向和开合状态已经有生成的参数结构，新的 `ACTUATORS` 层负责把这些参数变成受保护的机械动作。

整车联调时，每条记录都带上 Git 提交号、固件版本、板卡与接线、发送命令、收到的 ACK/telemetry 和实际动作。构建日志证明代码进入固件，串口抓包证明命令完成往返，轮位记录和视频证明机械动作符合预期。证据连成一条线，项目的完成状态也会自然变得清楚。

那条最初的 `START_MOTION` 已经从一个协议名称走到四路电机输出接口。继续沿着构建、验证、反馈和安全这条路线前进，它会逐渐从“写下电机输出”成长为“让机器人知道自己在做什么，并且能够可靠地停下来”。
